# NEAR Keys and Custody

NEAR has no Tendermint `priv_validator_key.json` and no double-sign slashing
equivalent, so the Cosmos rules do not transfer. What it does have is four
distinct secrets with very different blast radii. Treat them differently.

| Secret | File / location | What it controls | If leaked |
|--------|-----------------|------------------|-----------|
| Node key | `~/.near/node_key.json` | P2P identity of the host | peer impersonation, no fund or stake authority |
| Staking key | `~/.near/validator_key.json` | signs blocks/chunks/endorsements **as the pool** | another host can sign for your pool; no ability to move funds |
| Pool owner full-access key | keychain / `~/.near-credentials/` | full control of the owner account and therefore the pool | total loss — stake, fees, pool parameters |
| Ping / automation key | function-call access key | only the allowlisted methods on the pool contract | limited to those methods |

## Node key

Generated by `neard init`. It is the host's network identity. Copying it to a
second host that also runs on the same network causes peer-ID conflicts and
unstable connectivity. When you rebuild a host, generate a new one rather than
reusing the old.

## Staking key

`validator_key.json` must contain the **pool account**, not the owner account,
and the private field is named `secret_key`:

```json
{
  "account_id": "<pool-name>.poolv1.near",
  "public_key": "ed25519:...",
  "secret_key": "ed25519:..."
}
```

Rules that matter operationally:

- `chmod 0600`, owned by the `neard` service user.
- `neard` reads it only at startup. After any change: `systemctl restart neard`
  — `start` on an active unit is a no-op.
- **Never run two nodes with the same `validator_key.json` on the same
  network.** NEAR does not slash for equivocation the way Cosmos does, but two
  hosts signing for one pool produce conflicting work, degrade your production
  ratio and make incident diagnosis impossible. Before starting a replacement
  host, prove the old one is stopped:

  ```bash
  systemctl is-active neard        # on the old host
  pgrep -a neard                   # must return nothing
  ```

- Back it up encrypted, off-host. Losing it is recoverable — you can rotate the
  pool's staking key — but only by sending an on-chain transaction from the
  owner account, and you lose production until it lands.

## Pool owner key

This is the real crown jewel: it can change commission, change the staking key,
unstake, withdraw and delete. Keep it off the validator host.

- Store it in the local keychain (`sign-with-keychain`) on an operator
  workstation, or on a hardware wallet (`sign-with-ledger`).
- Do not place the owner's full-access key in `~/.near-credentials/` on a
  server that also runs `neard`.
- Consider a separate owner account from any treasury or hot account.

## Ping / automation key

The epoch `ping` must run unattended, which means a key lives on a machine. It
does not need to be a full-access key. Add a **function-call access key**
scoped to the pool contract and only the methods the automation needs:

```bash
near account add-key <owner>.near \
  grant-function-call-access \
  --allowance '1 NEAR' \
  --receiver-account-id '<pool-name>.poolv1.near' \
  --method-names 'ping' \
  autogenerate-new-keypair save-to-file ~/near-ping-key.json \
  network-config mainnet sign-with-keychain send
```

A function-call key cannot transfer NEAR. If the automation host is
compromised, the attacker can ping your pool — and nothing else.

Check what keys an account carries, and audit them regularly:

```bash
near account list-keys <owner>.near network-config mainnet now
```

Remove keys you no longer recognise:

```bash
near account delete-key <owner>.near ed25519:<public-key> \
  network-config mainnet sign-with-keychain send
```

## Backup checklist

Before any migration, rebuild or disk operation:

```bash
tar czf near-keys-$(date -u +%Y%m%dT%H%M%SZ).tar.gz \
  -C ~/.near node_key.json validator_key.json
sha256sum near-keys-*.tar.gz
```

Encrypt the archive, move it off the host, verify the checksum at the
destination, and delete the plaintext copy. `data/` is disposable and can be
re-synced; the key files are not.
